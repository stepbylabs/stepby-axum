# Axum 后台管理项目全局开发规则
## 核心目标
在当前 axum-backend 目录下，构建 **纯 Axum 0.8 + SeaORM 1.1** 生产级后端服务，接口对齐本项目前端 yebot-ui 调用规范，可直接联调运行。
仅允许修改 axum-backend 和 yebot-ui 目录，禁止修改任何 ref- 前缀的参考项目源码。

## 参考优先级（严格从高到低，禁止混淆）
1. **接口契约第一**：接口路径、请求方法、入参出参、分页格式、统一返回结构，对齐 ref-salvo-admin 的接口定义，保证与本项目前端 yebot-ui 无缝对接；字段类型优先从 yebot-ui 的 TS 定义中提取
2. **架构规范第二**：工程分层、目录结构、编码风格、中间件实现、错误处理、状态注入，优先参考 ref-soybean-admin 的 Axum 官方最佳实践
3. **同栈细节第三**：SeaORM 查询写法、事务处理、定时任务/数据权限的同栈实现细节，参考 ref-axum-admin 的原生 Axum 实现；仅按需参考指定模块，禁止全盘照搬架构
4. **边界补充第四**：业务规则、异常处理、级联逻辑存疑时，参考 ref-salvo-admin 的业务设计，但必须用 Axum + SeaORM 原生方式重写

## 绝对禁令（违反视为无效输出）
1. 禁止引入 salvo、rbatis 的任何运行时依赖和特有 API，包括但不限于：`#[handler]` 宏、Depot 容器、Salvo 专属 Request/Response、rbatis 注解式查询
2. 禁止直接复制粘贴任何参考项目的源码，所有逻辑必须用 Axum + SeaORM 原生方式重新实现
3. 禁止混合多种 ORM 写法，全程统一使用 SeaORM 进行数据库操作
4. 禁止在 Service 层、数据层引入任何 Axum/Web 相关类型，严格遵循单向分层依赖
5. 禁止参考 ref-axum-admin 的数据缓存、多部门切换、中间件函数抽象等冗余功能，只复用指定模块的业务实现思路
6. 禁止修改 yebot-ui 前端核心接口逻辑，后端必须主动适配前端约定

## 分层开发规范
1. Handler 层：仅负责参数解析、服务调用、结果封装，不包含任何业务逻辑
2. Service 层：承载全部业务逻辑、事务控制、参数校验，不依赖任何 Web 层类型
3. Repository 层：封装数据库查询操作，仅与 SeaORM 交互
4. 依赖方向：Handler → Service → Repository，禁止反向依赖

## 输出规范
1. 所有代码按「文件相对路径 + 完整代码块」格式输出，可直接一键创建文件
2. 代码符合 Rust 社区最佳实践，核心逻辑添加必要注释，错误处理完善，命名统一使用蛇形命名法
3. 每次生成完成后，必须按以上规则自查，在末尾标注「✅ 自查结果」，说明是否存在违规点与风险点
